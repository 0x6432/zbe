# ZBE Valgrind log authorship: next design

**2026-11-09 — source-reasoned design only.** No gate, build, compiler, test, CI, dispatch or probe was run for this review. No security property, local Valgrind version, host policy or readiness is proven. The preparation remains HELD.

## Decision and scope

The most promising *research* path is a pinned, independently audited Valgrind-core change that separates trusted log emission from **all** guest-origin syscall execution, combined with a separately protected collector and an independently verified kernel enforcement layer. It is not yet a feasible drop-in implementation: complete mediation, protected core state, peer policy, workload compatibility and end-to-end log delivery have not been established. A source-only feasibility study should precede any patch. If it cannot account for every route, stop; don't certify a partial filter. A stronger isolated execution environment may additionally contain peers, but alone cannot separate Valgrind core from its in-process client. Do not release HOLD or alter the gate based on this note.

The protected property is narrower than “the compiler is correct”: for each identified scan, bytes accepted as Valgrind diagnostics must be the complete ordered bytes emitted by the intended trusted Valgrind core for that scan, with no untrusted insertions, substitutions, omissions, replay or cross-case mix-ups. An authentic clean summary does not prove that the expected work actually ran, that input was not altered, or that Valgrind had no vulnerabilities. Those are separately required identity, workload, coverage and tool-trust assumptions.

## Evidence and what it does—and does not—show

- The original preparation uses `--log-file="$W/valgrind"`; `capture_command.py` runs `/usr/bin/valgrind` on the real compiler and copies the file **after** the process returns. `controller.py` checks the copied text and coverage. A copy and SHA-256 preserve bytes, not their author; an attacker able to affect the file before the copy can affect evidence. The harness also reads the original path, so protecting only the later copy does not protect the harness verdict. Sources: `preparation/capture_command.py`, `preparation/controller.py`, `preparation/reviews/primary/canonical-to-amended.diff`.
- The prior 3.19.0 review documents an inherited/high-FD pipe design, not a runtime measurement of the gate's `--log-file` path. Tagged `finalize_sink_fd()` duplicates the supplied FD into Valgrind's safe range but does not close the original. Generic `dup` validates its **result**, and `dup2` its **destination**, not the reserved source. Thus a high writer can be duplicated into a client-allowed low slot; direct writes to the reserved number are not the only route. The Linux `RLIMIT_NOFILE` boundary also depends on the 12-FD startup reservation and branch. [source: prior report] [1] [2]
- The prior synthetic native fixture reported that a narrow FD filter denied both synthetic core and client writes, while `/proc/self/fd/100` reopened a writer in that fixture. It did not use Valgrind or the production collector, and its seccomp rule was deliberately incomplete. Its observation does not establish host proc permissions or results for the real gate. Source: `/data/zbe-evidence-isolation-prototype/report.md`, `fixture.c`, and `results.txt`.
- Tagged `VG_(client_syscall)` describes pre-wrappers and passes guest calls to the kernel through both blocking and synchronous paths; the synchronous path invokes `VG_(do_syscall)`. Log delivery invokes `VG_(write)` from `send_bytes_to_logging_sink`. A proposed instruction-pointer split therefore needs an actual complete call graph, not an assumption that all guest syscalls and core log writes already have disjoint sites. The tagged code also has fallback-to-stderr behavior in some sink cases; missing output or such fallback must fail closed for evidence. [1] [3]

## Threat model and trust boundaries

Assume the exact real compiler process and inputs may be adversarial for evidence purposes: it controls guest instructions, registers, addresses, syscall arguments, client output and, where permitted, threads, signals and descendants. Assume an untrusted same-UID peer may try to interfere, unless independently excluded by the actual environment. A malicious client may seek a false clean scan, corrupt or suppress diagnostic bytes, spoof a completed case or prevent collection. The protected controller, collector, pinned reviewed Valgrind core/tool, Linux kernel and intended launcher are trusted components, not established secure by this note. Compromise of kernel, collector, launcher or Valgrind core/tool through a memory-safety or logic bug is outside the narrow claim and requires separate assessment; merely declaring core trusted does not demonstrate that guest-controlled data cannot corrupt it. Treat denial of service as a failed scan, not a security pass.

Attack surfaces include:

1. **Shared writer:** direct use or aliasing via `dup`, `dup2/3`, `fcntl(F_DUPFD*)`, inherited preexisting FDs, `SCM_RIGHTS`, `pidfd_getfd`, FD replacement/reuse, and write-capable interfaces such as `writev`, `splice`/`vmsplice` or `sendfile`, subject to actual syscall support. `/proc/self/fd` reopening depends on inode access; path/proc indirection, relative paths and mount namespaces complicate policy. Peer `/proc/<pid>/fd`, `/proc/<pid>/mem`, ptrace and pidfds have distinct checks; do not assume Yama, UID 999, `no_new_privs` or zero capabilities suffice. [4] [5]
2. **Trusted core impersonation:** guest reaches or manipulates an allowed raw syscall site, executable mapping, control flow, registers, buffers, shared state, signals, thread state or core memory; or induces a core helper to perform a guest-selected operation. An IP-only rule is a hypothesis, not authenticated origin. Formatting and client-controlled filenames/diagnostics may also generate core-authored text with attacker-influenced content; authentic bytes aren't necessarily truthful claims.
3. **Lifecycle and kernel coverage:** original and duplicate FDs, fork/clone with or without shared FD tables, exec/CLOEXEC, child tracing, multiple threads, signal/restart behavior, mapping changes, architecture/compat syscall ABI, async I/O/io_uring and descriptor-passing routes must be classified, including unsupported syscalls and unexpected errors. Reusing an FD number or blocking only a few write syscalls is not object-level isolation.
4. **Evidence handoff:** the collector can receive forged bytes from a leaked writer, drop/truncate bytes on errors or buffer exhaustion, or accept a stale/misassociated log. Even authentic collector bytes can later be replaced at `$W/valgrind`, or the harness and controller can read different bytes. A same-UID peer/descendant may race the handoff. EOF does not prove correct completion if an unintended writer persists or bytes were dropped. A valid-looking single zero summary is forgeable if output is not authentic.

## Options compared

### A. Audited core-mediated split + kernel enforcement — preferred research candidate

Make a **minimal, explicit core patch**, pinned to the actual source/build provenance, that gives core log emission a dedicated, auditable syscall path and ensures guest-origin requests—including wrapper-initiated syscalls on a guest's behalf, blocking and synchronous paths—cannot use it with guest-controlled arguments or access its protected state. After initialization, close the unnecessary supplied writer and retain only explicitly tracked writer(s); avoid creating low aliases. Establish how every guest-visible FD operation, open/proc access, descriptor passing and fork/exec path is denied or safely mediated. A kernel-enforced policy must backstop the separation, applied to every relevant task/thread and ABI, with FD lifetime and object identity protected. Illustrative IP-and-FD filtering is only a candidate: prove guest cannot reach or redirect the site or feed it arbitrary buffer/FD arguments, and that all other paths cannot access the writer. Core and client ordinarily share an address space and kernel identity, so this is a substantial security redesign, not a small change to `dup` wrappers.

Required composition: a protected collector starts with a one-case writer; all setup handoffs and closures are accounted for; only the reviewed core path can emit to it; capture detects partial writes, errors, timeouts and missing EOF, and binds complete bytes to the actual case and real process exit. Audit the tagged writer's return/error behavior: logging currently invokes `VG_(write)` without the shown caller checking its result, so reliable complete output must be explicitly designed rather than presumed [1]. If the core cannot enforce the origin distinction or protect its own state, reject this option. No claim is made that an implementation exists.

A broker in a separate task with its own FD table is helpful only if its inbound requests are authenticated as core-origin and guest code cannot send equivalent requests; a socket/pipe, random token, or sender UID shared with the guest does not by itself provide that guarantee. Modifying core exclusively to reject `dup*`, closing the original, or reserving a high number misses other routes and is insufficient.

### B. Trusted syscall separation / external observation — conditional fallback

A separately privileged monitor can consider ptrace or seccomp user notification to observe or mediate syscalls, but it sees real kernel operations made by Valgrind, not an intrinsic trustworthy “guest vs core” label. The tagged synchronous guest path can use common core syscall machinery [3]. A monitor would need a reviewed, non-spoofable origin signal or audited syscall-site separation, complete coverage for threads/fork/exec, stable mappings, state, buffer contents and result handling. Inspecting a write buffer at syscall entry alone is not proof of the bytes the kernel later consumed if another thread can mutate memory; partial writes, interruptions, changes to FD tables and race-free stop/resume must be handled. Kernel documentation warns that seccomp is not a sandbox; its notification CONTINUE mechanism carries an inherent TOCTOU risk. [6] [7]

This is an independent candidate only if it avoids modifying Valgrind; if origin distinction cannot be established externally, it is not independent of option A. Tracing may change scheduling, signal/ptrace relationships and workload behavior; whether it is contract-compatible is unknown. Treat per-case or complete execution tracing as research, not proof of origin or the scan itself. Logging stdout/stderr or post-hoc parsing alone does not solve origin.

### C. Stronger isolation — necessary complement, not a standalone fix

A disposable VM/microVM, protected collector outside the guest, unique per-job identity, restrictive peer/ptrace and proc policy, and tightly controlled descriptor inheritance can reduce host/peer exposure. None separates a same-process guest from an inherited logger FD or proves that bytes sent out of a VM came from its Valgrind core rather than the client. VM snapshots or externally read files have the same provenance problem when the client can write them. Changing UID, PPID, resource limits, namespace or process tree may violate the existing contract and needs explicit authorization and compatibility review. Avoid host-wide changes.

## Integrating without weakening the existing gate

Any eventual proposal is a separately reviewed replacement of the evidence path, not permission to modify or run the present gate. Preserve the actual compiler ELF/path and its exact argument bytes and environment needed by the workload; no compiler wrapper inside Valgrind, altered inputs, fake scans, skipped workloads, relaxed budgets or unapproved scheduling/process semantics. Verify actual ELF content/identity at execution, not just that a path appears in argv. Preserve every non-logging Valgrind option, status/signal and output semantics. Any logging-option transform or altered Valgrind core/build is a new reviewed deviation and must be pinned and accepted explicitly; existing exact-tree approvals do not approve it.

For each of the 76 input × six target × two optimization combinations, the protected collector must bind the bytes, command, actual process identity, exit/signal, and case ID to one fresh run without replay. Provide the unchanged harness with an immutable or equivalently protected exact byte snapshot **before** it reads `$W/valgrind`, then ensure the controller validates the same snapshot; the existing `: >` and temporary directory ownership, untrusted processes, peers and descendants make this a design problem, not an already-solved implementation. If this cannot be done without changing the harness contract, stop for approval and re-review. Fail closed on unsupported paths, missing collector, write/flush failure, fallback, incomplete EOF, extra writers, timeouts, malformed or cross-case data.

Do not weaken any existing checks. In particular: all 916 planned stages and their stage-specific checks; 526 rewrite unit tests in each specified mode, legacy unit and behavior checks, 26 classifier tests and input-error oracle; all 912 distinct real Valgrind cases, exactly one newline-terminated zero-error summary and fatal-tool rejection, statuses and signal semantics; exit 1 accepted only for the existing exact normalized-diagnostic, SIGABRT-confirmed C-reference input rejection; debug-info-degradation warning behavior; preserved raw outputs, build identity and source-before/after verification. The cited inventory and controller specify the remaining actual plan and checks; no count in this note replaces them. Existing 2-CPU/4-GiB local conditions, isolation and backup/seal requirements remain as recorded. The separate exact-SHA hosted workflow/job/step checks, expected conditional skips and no overlap/no retry restrictions in `ci-requirements.json` are unchanged. No historical result or synthetic fixture earns real-scan credit.

## Required independent reviews before any production-like use

1. **Valgrind/VEX and security reviewers**, independent of the patch author: pinned source/build correspondence, actual log call graph and errno/short-write behavior; syscall tables, wrappers and both synchronous/blocking paths; guest memory/control-flow isolation; every descriptor creation, transfer, duplication, use, replacement, mapping, fork/clone/exec and signal/restart path. Document what is explicitly unsupported and how it fails closed.
2. **Linux/kernel isolation reviewer**, independent of the core author: enforceability of origin distinction, every task/thread and architecture/ABI, process and FD-table lifetime, pointer and TOCTOU races, io_uring/async interfaces, procfs/pipe inode credentials, `SCM_RIGHTS`, same-UID peer ptrace/pidfd/proc policy and absence of inherited writer. Verify actual deployment LSM and credentials rather than assuming them; no system changes implied.
3. **Gate/evidence reviewer**, independent of implementer: launch, collector identity and ordering, loss detection and tamper-resistant handoff to both harness and controller; case binding; all existing correctness, diagnostic, signal, workload, environment, source-identity and hosted CI checks; full diff and preserved approvals/backup. A new core, wrapper, collector or process contract needs appropriate fresh approvals and updated seals. Existing two source-tree approvals are explicitly static-only and do not provide these approvals.
4. **Supply-chain/tooling reviewer**: source tag versus actual executable and distribution patches, tool/build recipe reproducibility, binary integrity, version/support/license implications and compatibility of the exact target workload. Current local binary, host security settings and deployment environment were not checked.

Separately authorized future validation would use isolated synthetic adversaries first: direct and alternate write/dup/transfer/reopen attempts, same-UID peers, fork/exec/thread races, FD reuse, partial writes and forced failures, malicious buffer changes and forged clean summaries; each must fail or become inconclusive, while a real trusted core clean/error log remains live and byte-complete. Then compare exact originals and all current positive and negative correctness checks. Passing these tests would be evidence, not a proof of security or authorization to run the held gate.

## Smallest next experiment — static only

In a new disposable workspace **outside the repository**, have an independent reviewer produce a source-level syscall-provenance table for the *exact proposed/pinned* 3.19.0 source and Linux x86-64 build: start at `send_bytes_to_logging_sink` and `VG_(client_syscall)`, trace both down to actual syscall instructions, and enumerate all wrapper-internal calls that can perform guest-requested operations. Identify every shared emission site and every unclassified route, including fd acquisition/transfer and fork/exec. Record source commit/blob IDs, exact line references, assumptions and one counterexample or unresolved item per proposed separation; independently cross-check the table against syscall tables and generated/platform-specific code. No compiling, executing, attaching to processes, touching the repo/index, modifying host security, accessing credentials/private-auth, or running any gate. This static review can only produce **candidate / blocked / unknown**, not establish runtime enforcement. Its go/no-go question: can every guest-origin syscall be routed or classified separately from the logger without changing the compiler/workload and without unreviewed guest-controlled access to the trusted site? If not fully answered, remain blocked. This is a proposed next step, not work executed here.
