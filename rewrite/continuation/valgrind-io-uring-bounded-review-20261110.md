## Evidence and conditional route

1. The AMD64 Valgrind table exposes `io_uring_setup`, `io_uring_enter`, and `io_uring_register` ([table 875–877](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-amd64-linux.c#L875-L877)). Setup checks the **returned ring FD** against `fd_allowed`; enter checks registers and the optional signal pointer, but its displayed complete PRE/POST bodies contain no SQE inspection or target-FD check. Register's `REGISTER_FILES` case annotates an integer array with `PRE_MEM_READ` but has no `fd_allowed` check on its entries ([wrapper 13201–13273](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-linux.c#L13201-L13273)). Compare the ordinary guest `write` wrapper, which applies `fd_allowed` to its FD ([4277–4299](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-generic.c#L4277-L4299)). This is a statement about these wrapper bodies, not all possible layers of enforcement.
2. These three PRE wrappers do not set `SfMayBlock` or complete the syscall. With initial flags zero and normal dispatch, the request is sent through the synchronous `VG_(do_syscall)` path ([initialization and pre-handler 2205–2252](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-main.c#L2205-L2252), [dispatch 2287–2302](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-main.c#L2287-L2302), [sync 2367–2379](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-main.c#L2367-L2379)). The AMD64 generic helper reaches the `syscall` instruction at [m_syscall.c:502](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syscall.c#L484-L503), also used by normal file/FD logging through [`VG_(write)`](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_libcprint.c#L587-L604), [`VG_(do_syscall3)`](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_libcfile.c#L294-L311), and [`VG_(do_syscall)`](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syscall.c#L1127-L1140). An IP-only core/guest label is therefore unsound; a policy additionally filtering syscall number and other arguments is a different proposal, not automatically defeated by this overlap.
3. Conditional counterexample to a **narrow** policy: suppose a live writer FD `H` is present in the kernel FD table; an adversarial guest knows `H`, obtains or already has a usable ring, can map/use its SQ and SQEs, and the kernel and policy permit the operations. Guest submits an `IORING_OP_WRITEV` SQE naming `H` (and suitable buffers and valid operation parameters), then invokes `io_uring_enter` on the ring. The Valgrind enter wrapper above does not apply the ordinary write wrapper's FD check to that SQE. In the chosen kernel, `io_uring_enter` submits SQEs ([9934–9993](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/fs/io_uring.c#L9934-L9993)); SQEs come from user-mapped memory ([7230–7252](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/fs/io_uring.c#L7230-L7252), [7261–7290](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/fs/io_uring.c#L7261-L7290)); `WRITEV` needs a file ([935–942](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/fs/io_uring.c#L935-L942)) and the non-fixed lookup uses `fget(sqe->fd)` ([7098–7102](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/fs/io_uring.c#L7098-L7102), [6862–6881](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/fs/io_uring.c#L6862-L6881)). After preparation, the opcode reaches `io_write` ([6361–6373](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/fs/io_uring.c#L6361-L6373), [6635–6656](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/fs/io_uring.c#L6635-L6656)), which checks write mode and may invoke the file's write operation ([3573–3577](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/fs/io_uring.c#L3573-L3577), [3595–3602 and 3619–3639](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/fs/io_uring.c#L3595-L3639)). Whether an actual sink, offset, buffer, CQ result, and policy permit a successful write remains unmeasured. This is not proof of a successful write or of any present gate compromise.
4. Fixed files add a distinct lifetime problem: on this kernel, permitted `IORING_REGISTER_FILES` copies each FD from user memory, calls `fget`, and stores the resulting file in a fixed table ([8212–8255](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/fs/io_uring.c#L8212-L8255), [8265–8269](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/fs/io_uring.c#L8265-L8269)); the fixed lookup uses that table ([6844–6859](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/fs/io_uring.c#L6844-L6859)). Subject to successful registration and lifetime semantics, later closing or reusing the numeric `H` does not by itself prove that all retained file references or queued work are gone. This is not an exhaustive ring-lifetime analysis.
5. In this pinned kernel, seccomp BPF cannot dereference pointers ([documentation 16–28](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/Documentation/userspace-api/seccomp_filter.rst#L16-L28)); `io_uring_enter` identifies the **ring FD**, not each SQE target FD. Thus a simple syscall-argument rule that protects `H` for `write`/`writev` but permits unrestricted io_uring submission cannot inspect the SQE's target through ordinary seccomp BPF. The source identifies a condition that a complete policy must handle, not a bypass of policies which deny or otherwise safely mediate io_uring. The kernel's user-notification CONTINUE warning also explicitly describes pointer TOCTOU ([header 80–96](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/include/uapi/linux/seccomp.h#L80-L96)).

Any denial may change workload semantics and requires approval. This is a review requirement, not a feasibility claim.
