# Valgrind evidence isolation — bounded log-position review

**Disposition: BLOCKED.** This is unreviewed source-only analysis, not a runtime demonstration, a complete security review, or evidence about the actual gate binary, kernel, sink, filesystem, policy or collector. No gate, attachment or security probe was run. HOLD remains unchanged.

## Sources and route

Valgrind source is the 3.19.0 mirror commit `8d3c8034b87db7b1d47285b053a05e6ad277c0d1`, with wrapper blobs pinned in `valgrind-syscall-provenance.md`. Comparison Linux source is upstream v5.15 commit `8bb7eca972ad531c9b149c0a51ab43a417385813`; commit-pinned `fs/read_write.c` has Git blob `af057c57bdc6447177bfc03e276ba2cd63bd9401`, matched to GitHub's contents API blob identity. This is a public-source identity check, not independent review or deployed-binary identification.

The AMD64 table selects [`sys_lseek`](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-amd64-linux.c#L482). Its [complete PRE wrapper](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-linux.c#L4175-L4181) checks argument definedness but neither calls `fd_allowed` nor sets `SfMayBlock` or a result. As traced in the existing provenance report, a guest call handed to the kernel without `SfMayBlock` goes through [`VG_(do_syscall)`](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-main.c#L2367-L2380) and reaches the generic syscall instruction also used for normal core log writes. The syscall number still differs; common source instruction alone does not defeat a policy also checking syscall and object.

The selected Linux [`lseek` path](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/fs/read_write.c#L291-L324) uses the FD's file object and invokes its seek operation if supported. The common [`generic_file_llseek`](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/fs/read_write.c#L54-L65) updates that file object's position; [`ksys_write`](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/fs/read_write.c#L636-L650) uses and advances the position where applicable. The 3.19.0 file logger opens with `O_CREAT|O_WRONLY|O_TRUNC`, not `O_APPEND`, and its ordinary logger writes through the sink FD ([open](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_libcprint.c#L353-L371), [write](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_libcprint.c#L587-L604)).

Conditional concern: **if** the guest can select the live numeric logger FD (or an alias sharing its open-file description), the descriptor points to a seekable file whose actual seek/write semantics behave as above, and the policy permits the call, a guest seek can reposition the logger before a later core write, potentially overwriting earlier diagnostics or creating a gap. This requires correct timing and actual filesystem/FD behavior; concurrency and other seeks/writes complicate it. It neither establishes arbitrary-byte injection nor proves any actual host is vulnerable. Pipes/sockets may not be seekable and need separate analysis. A rule trusting all operations at the generic logger syscall instruction, or treating only guest writes as potentially evidence-modifying, must consider this route; a tighter policy has not been analyzed or disproven here.
