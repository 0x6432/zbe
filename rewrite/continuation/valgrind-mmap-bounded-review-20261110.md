## Bounded path

- The AMD64 table selects `sys_mmap` ([table](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-amd64-linux.c#L479-L483)); its [PRE wrapper](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-amd64-linux.c#L403-L415) passes the six client arguments into `ML_(generic_PRE_sys_mmap)` and completes the call with its returned status. The [complete generic helper](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-generic.c#L2297-L2483) contains address/advisory checks and passes the guest FD `arg5` to `VG_(am_do_mmap_NO_NOTIFY)` ([2384–2388](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-generic.c#L2384-L2388)); there is no `fd_allowed` call in this wrapper/helper body. This is not a claim that other kernel or policy layers permit the operation.
- On AMD64/Linux, [`am_do_mmap_NO_NOTIFY`](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_aspacemgr/aspacemgr-common.c#L142-L162) invokes `VG_(do_syscall6)(__NR_mmap, ..., fd, offset)`. The [macro](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/pub_core_syscall.h#L81-L84) reaches `VG_(do_syscall)`, the generic core path also used by normal log writes as documented in the existing provenance report. This is another guest-triggered core-site syscall, not evidence that an IP-plus-syscall-and-object policy necessarily fails.
- Conditional threat: if the guest can obtain an **O_RDWR** descriptor referring to the actual writable regular log file, the file has a suitable existing mapped range, the filesystem supports shared writable mappings, and all address, permission, LSM, kernel and policy checks allow it, a `MAP_SHARED | PROT_WRITE` mapping can provide a file-modification route without subsequent guest `write` calls. The compared kernel obtains a file reference for a mapped VMA ([1786–1787](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/mm/mmap.c#L1786-L1787)); closing a numeric descriptor does not by itself remove an already established mapping. A policy protecting only a logger FD number or ordinary write syscalls must therefore account for aliases and mappings; this does not prove any concrete policy can be bypassed or any log was modified.
- Important restriction: the [logger opens its file `O_WRONLY|O_CREAT|O_TRUNC`](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_libcprint.c#L353-L370). In the selected Linux source, a shared writable file mapping requires `FMODE_WRITE` and also falls through to an `FMODE_READ` check ([1489–1523](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/mm/mmap.c#L1489-L1523)), so this observation does **not** show that the original write-only FD can itself form the mapping. A separate readable/writable alias is a necessary assumption for the example; whether one can be obtained is unknown. In particular, the initially truncated file, file growth, EOF/SIGBUS behavior, existing mappings, path/object identity, permissions, peers, and synchronization must not be assumed away.
