## Bounded observation

The pinned AMD64 table maps `open`, `write`, `lseek` and `openat` ([table](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-amd64-linux.c#L470-L482), [openat](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-amd64-linux.c#L781)). In the displayed [open wrapper](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-generic.c#L4193-L4256) and [openat wrapper](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-linux.c#L5694-L5787), special substitutions are shown for selected proc files, but no `/proc/self/mem` substitution or explicit pathname denial appears in those bodies. Normal open/openat dispatch is marked blocking; the post-wrapper checks the **returned FD** with `fd_allowed`. The displayed [`lseek` wrapper](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-linux.c#L4175-L4183) performs register annotation; ordinary [`write` checks the supplied FD](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-generic.c#L4277-L4299). These statements do not classify other interception, kernel or policy layers.

In the comparison Linux source, [`mem_open` → `proc_mem_open` → `mm_access`](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/fs/proc/base.c#L794-L833) requests attach-mode access using filesystem credentials. The [`mm_access` comparison](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/kernel/fork.c#L1315-L1332) calls `ptrace_may_access` only if the acquired target mm differs from current mm. The proc-memory operations provide seek and write; on write, [`mem_rw` requests `FOLL_FORCE | FOLL_WRITE`, copies the input to a page, and calls `access_remote_vm` at the file position](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/fs/proc/base.c#L835-L930). The selected kernel's [`__access_remote_vm`](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/mm/memory.c#L5118-L5180) attempts to pin a remote page, then copies to it on successful write, with a configuration-dependent alternate VM-operation path. `FOLL_FORCE` does not establish that arbitrary mappings are writable: detailed VMA, page, configuration and permission constraints still apply.

## Question for a proposed isolation design

If a guest can open an applicable proc-memory path, obtain an FD permitted by Valgrind, choose an offset corresponding to usable core-owned memory, and pass every actual kernel, mount, LSM, syscall, mapping and policy restriction, can seek/write alter core logging state? The cited wrapper bodies alone do not answer this for a deployed setup. A policy preventing or race-freely mediating proc-memory access, denying relevant calls, or otherwise excluding the prerequisites is not defeated by this observation. Merely relying on an external-process ptrace restriction or protected high logger-FD number is not, by itself, demonstrated to exclude same-mm proc-memory access.

Review must classify proc namespace/path variants and aliases, already-open or transferred FDs, seek and positional writes, all tasks and lifecycle paths, mapping restrictions, actual kernel/LSM, legitimate workload compatibility and fail-closed policy. The existing process-memory, FD, io_uring, collector and protected-handoff questions remain open. No successful core-memory access or evidence tampering is claimed.
