## Bounded source observation

The AMD64 table registers `process_vm_writev` ([841–846](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-amd64-linux.c#L841-L846)). Its [PRE wrapper](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-linux.c#L6341-L6366) reads register metadata, annotates local and remote iovec arrays, and annotates local source buffers after `safe_to_deref`; its displayed body contains no test of the remote PID, remote target addresses, or Valgrind-owned memory. It does not set `SfMayBlock` or complete the request itself. Under normal dispatch with no other interception or failure, the request takes the synchronous generic `VG_(do_syscall)` route previously traced to the same source-level syscall instruction used by normal file/FD logging; this is not proof of compiled instruction addresses or of absence of another protection layer.

In the selected Linux comparison source, the syscall copies user-supplied iovec arrays and invokes `process_vm_rw_core` with write direction ([258–283, 298–303](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/mm/process_vm_access.c#L258-L303)); that function looks up the target and calls `mm_access(..., PTRACE_MODE_ATTACH_REALCREDS)` before processing remote vectors ([195–217](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/mm/process_vm_access.c#L195-L217)). `mm_access` calls `ptrace_may_access` only if the target mm differs from `current->mm` ([1315–1332](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/kernel/fork.c#L1315-L1332)). The write path requests `FOLL_WRITE` remote pages and, subject to page pinning/copy success, writes from the local iterator into those pages ([70–127](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/mm/process_vm_access.c#L70-L127), [27–52](https://github.com/torvalds/linux/blob/8bb7eca972ad531c9b149c0a51ab43a417385813/mm/process_vm_access.c#L27-L52)).

Conditional question for a proposed design: if the guest can select a target task whose mm is the Valgrind process mm, determine a writable core-state address, provide valid local/remote vectors, and pass every actual syscall, page, security and environment restriction, can it change that state via this path despite any guest-address-space translation checks? The checked wrapper body alone does not establish the answer. Shared-mm handling in this kernel means an external same-UID/ptrace restriction is not by itself a demonstrated substitute for mediating self-targeted writes. A policy denying or safely mediating this syscall is not defeated merely by this observation. No claim is made about actual mappings, available PID, version-specific behavior, successful page pinning, syscall execution or compromise.

Review must also classify the read variant, other process-memory interfaces, possible indirect core-state modification, vector races, all tasks and lifecycle paths, actual kernel/LSM, legitimate workload needs and fail-closed behavior, plus the previously documented FD, io_uring and collector routes. A comprehensive independently reviewed classification and protected handoff remain required before any gate. This is not the independent terminal audit.
