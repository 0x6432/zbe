# Valgrind 3.19.0 syscall provenance — static research

**Disposition: BLOCKED** for an origin-authenticating or complete-mediation design. **Candidate:** a separately audited core redesign with a genuinely dedicated logging path, protected state, and complete mediation. **Unknown:** whether such a redesign is feasible without changing workload semantics and whether any deployment uses this source. This is not a security proof or a runtime finding. HOLD remains unchanged.

## Concrete counterexample to naïve IP filtering

Suppose a policy trusts **all operations** at the generic logging syscall site as core-only and blocks guest `write` only when its FD equals the high reserved logger FD `H`. If `H` is open and the guest can choose its numeric value, `dup2(H, L)` for an available, client-allowed low `L` is sent through the synchronous route: its [pre-wrapper checks the *destination* `L`, not the source `H`, and sets no `SfMayBlock`](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-generic.c#L3389-L3402). It reaches the **same line-502 instruction as the logger**. `dup(H)` has no source-FD check and checks only the returned FD in its post-wrapper at [3371–3386](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-generic.c#L3371-L3386). If the kernel permits the duplication and `L` passes [`fd_allowed`](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-generic.c#L1399-L1416), guest `write(L, bytes, n)` passes the FD check and takes the blocking path ([write wrapper](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-generic.c#L4277-L4299)). This is a **conditional source-reasoned bypass** of that specifically described naïve policy, not a measured exploit, not a bypass of every IP+syscall+object policy, and not evidence guest `write` itself uses line 502. Denying all guest-site writes would break ordinary client output; a narrower carefully designed policy is not analyzed or proven here.

A second route to classify: AMD64 table selects `sendfile`; its [pre-wrapper marks it blocking but does not call `fd_allowed` for `out_fd`](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-linux.c#L1590-L1600). Subject to compatible FDs, kernel behavior and policy, `sendfile(H, input, ...)` is a guest-requested write-like operation even without a low alias. This is not a claim that the local kernel or any specific sink supports or permits it.

## FD acquisition, transfer, and lifecycle

- [`prepare_sink_fd`](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_libcprint.c#L353-L371) uses `VG_(open)` with create/write/truncate; on AMD64/Linux [that helper invokes generic `__NR_open`](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_libcfile.c#L231-L239), at line 502. [`finalize_sink_fd`](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_libcprint.c#L412-L425) calls `fcntl(F_DUPFD, fd_hard_limit)`, sets `FD_CLOEXEC` on the new FD, stores it, and has no close of the supplied original in that function. The [fcntl helper](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_libcfile.c#L671-L684) also reaches line 502. Whole-lifecycle disposition of the original needs independent tracing; do not infer it from this function alone. `F_DUPFD` failure reverts to stderr.
- `dup2` and `dup` as above; [`dup3` checks destination only](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-linux.c#L3914-L3927). [`fcntl` accepts `F_DUPFD` and `F_DUPFD_CLOEXEC`, checks resulting FD afterward, and marks only `F_SETLKW` blocking on this platform](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-linux.c#L6794-L6824); [post-check](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-linux.c#L6899-L6925). Aliasing remains conditional on actual limits and descriptors.
- Normal guest [`open`](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-generic.c#L4193-L4254)/[`openat`](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-linux.c#L5694-L5787) go through blocking dispatch and check the result; special `/proc/self/{cmdline,auxv,exe}` cases instead issue core `VG_(dup)` on Valgrind-maintained descriptors, then return early. This is an additional *guest-triggered core-site FD acquisition*, not a claim that these special descriptors are the log writer. Reopening `/proc/self/fd/H`, paths to the log file, proc indirection and inode permissions remain deployment-dependent, not assumed effective or ineffective.
- [`sendmsg` and `recvmsg`](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-linux.c#L5598-L5620) use blocking dispatch. Post-receive [`check_cmsg_for_fds`](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-generic.c#L1100-L1120) detects `SCM_RIGHTS`, optionally records received FDs, and contains a TODO about `fd_allowed`; it does not establish transfer is possible in a particular environment. Trace peer availability, sender/receiver descriptors, control-buffer races and sendmmsg/recvmmsg separately.
- [`splice` checks both FDs; `vmsplice` checks the FD and itself invokes `VG_(fcntl)(F_GETFL)`](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-linux.c#L6664-L6711), which reaches generic line 502. Checks based on a number do not establish object identity. Also classify `writev`, `pwrite*`, `tee`, `copy_file_range`, `sendfile`, `open_by_handle_at` and `io_uring` SQEs. The table contains [`io_uring_setup/enter/register`](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-amd64-linux.c#L869-L880), and [register inspects files](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-linux.c#L13201-L13268); no assertion here of complete mediation of SQEs.
- [`close_range` pre-wrapper makes core generic syscalls for split ranges and excludes known sinks](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-linux.c#L13355-L13396); FD reuse and all flags still need review. [At-fork logging](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_libcprint.c#L427-L471) can suppress output or reopen a changed expanded filename. `FD_CLOEXEC` on the duplicate does not imply its closure at fork, closure of other aliases, or protected collector EOF.
- The [AMD64 syscall table](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-amd64-linux.c#L464-L900) includes `clone3` as `sys_ni_syscall`; `pidfd_getfd` and `openat2` have no table entries in this snapshot. Missing entries produce [`ENOSYS` via `bad_before`](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-main.c#L1886-L1906), with [lookup fallback](https://github.com/unofficial-mirror/valgrind/blob/8d3c8034b87db7b1d47285b053a05e6ad277c0d1/coregrind/m_syswrap/syswrap-main.c#L1955-L1957). This is scoped to normal guest syscall dispatch in this source; it does not exclude peer operations, other ABIs, generated paths or changed versions.

## Unresolved routes and specific next step

1. **Unknown / incomplete enumeration:** `wrapper-call-sites.txt` lists 81 syntactic matches for selected syscall-capable helpers in three wrapper files; `all-direct-vg-call-sites.txt` lists 556 `VG_` call lines and `amd64-syscall-table.txt` lists 312 matching table lines. These are search inventories, not a call graph: macros, `ML_` calls, tool callbacks, function pointers, helpers outside those files, conditionals and compiler-generated paths may lead to syscalls. `assembly-candidate-sites.txt` is a deliberately noisy keyword list, not a validated list of instructions. The displayed example rows are not exhaustive. Platform-specific/generated VEX and startup, scheduler, signal, gdbserver, tool and child paths need classification.
2. **Unknown / process and object boundary:** permitted control-flow/memory access from the guest to core state or a proposed dedicated instruction; syscall return/restart behavior, multi-thread races and buffer mutability; Linux seccomp instruction-pointer reporting at the actual compiled instruction; FD identity, fork/shared tables, exec, peer `/proc`, ptrace and descriptor transfer. Actual log handoff, truncation/errors and fallback are not solved. No local binary, host settings or credentials were inspected.
3. **Next source-only action:** an independent Valgrind/VEX reviewer should use the pinned commit and the inventories to walk **every AMD64 table entry**, resolve all PRE/POST and nested `VG_`/`ML_`/tool helpers through platform conditionals to syscall instructions, and label each syscall and FD source/sink/transfer, including io_uring and fork/exec/signal paths. Produce a checked row per entry and a list of direct assembly sites across all compiled core/VEX files, explicitly marking dynamic/generated code and unknowns. Separately review guest control of the proposed dedicated path and state. If any route cannot be classified or made fail-closed without an unapproved workload change, keep **BLOCKED**. Only after this source review can a separately authorized feasibility design be considered; no gate or production-like execution is authorized by this report.
